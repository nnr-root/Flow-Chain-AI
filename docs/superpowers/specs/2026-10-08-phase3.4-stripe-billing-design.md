# Phase 3.4 — Payments, Subscriptions and Automated Credit Billing — Design

Date: 2026-10-08 · Status: approved (sections 1–4), prototype pending · Builds on Phase 3.3 (`4739405`)

## 1. Goal

Let users pay for credit themselves: monthly subscriptions and one-off top-ups through Stripe Checkout, turned
into credit automatically and exactly once, with the plan, the split balance and the payment history on
`/account`. Credit granted by hand (`studio:grant`) keeps working.

The pipeline, reservations as an idea, tenant isolation and the queue's rules do not change. Paid actions still
only ask whether the balance covers a cap.

### Non-goals (later)

Feature gates or higher limits per tier; currencies other than USD; taxes and invoices beyond what Stripe
issues; coupons and trials; mid-month plan changes with proration; team billing; automatic handling of a
dispute that is won; dunning emails of our own.

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | **The web receives, the worker fulfils.** The webhook route verifies Stripe's signature and passes only the event id to the worker, which fetches the event from Stripe and calls one SQL function | the worker stays the only holder of the key that grants credit; whoever can write to Redis cannot mint credit, because the worker asks Stripe |
| D2 | Billing is on when `STRIPE_SECRET_KEY` is set, and requires accounts (3.3) | without it the studio is exactly 3.3 |
| D3 | **Margin is a mark-up at purchase:** a payment grants the credit its Stripe price says (`credit_usd` in the price's metadata), less than was paid | prices on the studio's buttons stay the real cost; nothing in pricing, caps or settling changes |
| D4 | **Two kinds of credit, one balance:** `plan_credit_usd` is the part of `balance_usd` that came from the current subscription month and expires at renewal; top-up and granted credit never expires; plan credit is spent first | the user never loses credit they bought separately |
| D5 | A reservation records how much of its cap was plan credit and in which month (`plan_part_usd`, `plan_period`); what is left of that part is returned only if the month is still current | expiring credit held by a job across a renewal must not come back as permanent credit |
| D6 | **Every fulfilment is keyed by the Stripe event id** (`stripe_events`), in the same transaction as its effect | a repeated delivery grants nothing twice |
| D7 | **Stripe is the source of truth** for prices, plans and subscription state; the database mirrors what the worker fetched fresh from Stripe, never an event's snapshot | Stripe does not guarantee the order of events |
| D8 | Who a payment belongs to comes from the Stripe customer's metadata (`user_id`), set by the worker when it creates the customer | a user cannot claim another customer and collect their renewals |
| D9 | Credit follows a **paid invoice** (a new subscription or a monthly cycle) or a **paid Checkout session** (a top-up), nothing else | a subscription that exists but is unpaid grants nothing |
| D10 | Plan switches take effect at the next renewal (Customer Portal without proration); cancelling keeps the plan until the period ends | there is never a partial month to compute |
| D11 | A refund or a dispute takes back the credit its payment granted, in proportion; a balance may go below zero | the owner is not left paying for refunded credit |
| D12 | The worker also lists Stripe's events of the last three days at start and every hour and fulfils any it has not recorded | correctness does not depend on webhook delivery |
| D13 | One subscription per user; USD only; amounts to four decimals | scope |
| D14 | `npm run stripe:setup` creates the products, prices, portal configuration and webhook endpoint from `billing/plans.json` | no dashboard work, and the test and live accounts are set up the same way |
| D15 | Tests use a stand-in Stripe (a local server answering the calls the studio makes), with events signed the real way | everything but Stripe itself is verifiable offline |

## 3. Architecture

```
browser ──▶ web ──(Checkout / Portal session)──▶ Stripe ──(webhook)──▶ web ──(event id)──▶ worker
                                                    ▲                                        │
                                                    └──────────── fetch the event ───────────┤
                                                                                             ▼
                                                                                  Postgres (fulfil_*)
```


## 4. Database

### 4.1 Changes and new tables

| Table | Change |
|---|---|
| `users` | `stripe_customer_id text unique`, `plan_credit_usd numeric(12,4) not null default 0`, `plan_period integer not null default 0` |
| `reservations` | `plan_part_usd numeric(12,4) not null default 0`, `plan_period integer not null default 0` |
| `ledger` | kinds gain `purchase`, `plan`, `expire`, `refund` |
| `subscriptions` (new) | `user_id` primary key, `stripe_subscription_id` unique, `plan`, `price_id`, `status`, `current_period_end`, `cancel_at_period_end`, `updated_at` |
| `payments` (new) | `id text` primary key (the Stripe invoice or Checkout session id), `user_id`, `kind` (`topup`/`plan`), `plan`, `paid_usd`, `credit_usd`, `refunded_usd` default 0, `taken_back_usd` default 0, `charge_id`, `invoice_url`, `created_at` |
| `stripe_events` (new) | `id text` primary key, `type`, `user_id`, `outcome`, `created_at` |

Row-level security: users select their own `subscriptions` and `payments`; `stripe_events` has no policy.

### 4.2 Accounting

`balance_usd` is everything the user may spend now. `plan_credit_usd` is how much of it expires with the
current subscription month (never more than the balance when the balance is positive).

| Event | `balance_usd` | `plan_credit_usd` |
|---|---|---|
| top-up or manual grant of `x` | `+x` | — |
| reserve a cap `c` | `−c` | `−p`, where `p = least(c, plan_credit_usd)`; the reservation stores `p` and the user's `plan_period` |
| settle at charge `k`, same `plan_period` | `+(c − k)` | `+(p − least(k, p))` |
| settle at charge `k`, after a renewal | `+(c − k) − (p − least(k, p))` | — (the unused plan part expires; an `expire` ledger row) |
| a subscription month starts, granting `g` | `−plan_credit_usd` (an `expire` row), then `+g` | `= g`; `plan_period + 1` |
| the subscription ends | `−plan_credit_usd` | `= 0`; `plan_period + 1` |
| refund of fraction `f` of a payment that granted `g` | `−(f·g − taken_back_usd)` | for a plan payment of the current month: reduced by the same amount, not below 0 |

### 4.3 Functions (all `security definer`, `search_path = ''`)

For `service_role` only. Each fulfilment function first inserts the event id into `stripe_events`; when it is
already there it returns `'duplicate'` and does nothing else.

| Function | Does |
|---|---|
| `link_stripe_customer(p_user_id, p_customer_id)` | sets `users.stripe_customer_id`; raises `customer_taken` when the customer belongs to another user, `already_linked` when the user has a different one |
| `fulfil_topup(p_event_id, p_user_id, p_payment_id, p_paid_usd, p_credit_usd, p_charge_id, p_invoice_url)` | balance `+credit`; a `payments` row; a `purchase` ledger row. A payment id that exists (another event for the same payment) grants nothing |
| `fulfil_plan_invoice(p_event_id, p_user_id, p_invoice_id, p_subscription_id, p_plan, p_price_id, p_paid_usd, p_credit_usd, p_period_end, p_charge_id, p_invoice_url)` | expires the remaining plan credit, `plan_period + 1`, grants the new month's, records the payment, upserts the subscription as `active` |
| `sync_subscription(p_event_id, p_user_id, p_subscription_id, p_plan, p_price_id, p_status, p_period_end, p_cancel_at_period_end)` | upserts the subscription row; grants nothing |
| `end_subscription(p_event_id, p_user_id, p_subscription_id)` | expires the remaining plan credit, `plan_period + 1`, marks the subscription `canceled` |
| `refund_payment(p_event_id, p_charge_id, p_refunded_usd)` | finds the payment by charge; takes back `credit × refunded/paid − taken_back_usd` |

`reserve_credit` and `settle` change as in §4.2. `grant_credit` is unchanged (permanent credit).

## 5. Fulfilment

### 5.1 The webhook route

`POST /api/stripe/webhook`: public, no session, no same-origin check (Stripe is neither a user nor a page); the
host rule applies; the raw body is read up to 1 MB; the `Stripe-Signature` header is verified (HMAC-SHA256 over
`<timestamp>.<body>` with `STRIPE_WEBHOOK_SECRET`, five-minute tolerance, constant-time comparison). A failure
answers 400 and nothing is queued. Otherwise a quick job `stripe-event` carries the event id to the worker and
the route answers what the worker says: 200 when fulfilled, ignored or a duplicate; 503 when the worker is away
or fulfilment failed (Stripe retries).

### 5.2 Events

| Event | Fulfilment |
|---|---|
| `checkout.session.completed`, `checkout.session.async_payment_succeeded` with `mode = payment` and `payment_status = paid` | `fulfil_topup` |
| `invoice.paid` with `billing_reason` `subscription_create` or `subscription_cycle` | `fulfil_plan_invoice` |
| `customer.subscription.created`, `customer.subscription.updated` | `sync_subscription` |
| `customer.subscription.deleted` | `end_subscription` |
| `charge.refunded` | `refund_payment` with the charge's `amount_refunded` |
| `charge.dispute.created` | `refund_payment` with the disputed amount |
| anything else | recorded as ignored; 200 |

### 5.3 How the worker fulfils an event

1. `GET /v1/events/<id>`: an id Stripe does not know is refused. The event's `livemode` must match the key's.
2. The objects are fetched fresh (the customer; the invoice or session with its line items and prices; the
   subscription), not read from the event's snapshot.
3. The user is `customer.metadata.user_id` (a UUID); a customer without one is ignored.
4. The credit and the plan name are the price's `metadata.credit_usd` and `metadata.plan`; the price must be
   the studio's (`metadata.studio = "flowchain"`). A price without a credit amount fails the fulfilment (it is
   retried), never grants nothing silently.
5. The SQL function for the event's type.

### 5.4 The catch-up

At start and every hour the worker lists `GET /v1/events` for the types of §5.2 created in the last 72 hours
and fulfils those whose id is not in `stripe_events`.

### 5.5 The customer

A quick job `stripe-customer` (the user's id from the session): the worker returns `users.stripe_customer_id`,
or creates a customer with `metadata.user_id` and the user's email under the idempotency key
`flowchain-customer-<userId>`, links it, and returns it.

## 6. The web

| Route or page | Does |
|---|---|
| `/pricing` | the catalogue: plans and top-ups with price and credit; public; buying needs a session |
| `POST /api/billing/checkout` `{ priceId }` | the price must be in the catalogue; a user with a live subscription is refused a second one (`already_subscribed`); creates a Checkout session (`mode` by the price's kind, the user's customer, `client_reference_id` = user id, success `/account?paid=1`, cancel `/pricing`) and returns its URL |
| `POST /api/billing/portal` | a Customer Portal session for the user's own customer, returning to `/account` |
| `/account` | the plan (name, status, renews or ends on), the balance split (plan credit and when it expires; permanent), the payments (date, what, paid, credit, refunded, invoice link), "Manage subscription"; with `?paid=1` a note that the payment is being confirmed and a refresh until the balance changes |

The catalogue is `GET /v1/prices?active=true&expand[]=data.product` filtered to the studio's, cached five
minutes. New error codes: `billing_unavailable` (503), `already_subscribed` (409).

## 7. Setup (`npm run stripe:setup`)

`billing/plans.json`: `{ plans: [{ key, name, monthlyUsd, creditUsd }], topups: [{ key, name, priceUsd, creditUsd }] }`.
Defaults: Starter $19 → $12, Pro $49 → $35; top-ups $10 → $6, $25 → $16. The command lists what exists in
Stripe (by `metadata.studio` and `metadata.key`), shows what it would create or replace (a price whose amount
or credit changed is archived and a new one created), asks, then creates products and prices, the portal
configuration (plan switches at period end without proration, cancel at period end) and the webhook endpoint
for `https://<STUDIO_HOST>/api/stripe/webhook`, writing the endpoint's signing secret to `.env`.

## 8. Failure handling

| What happens | Result |
|---|---|
| the worker is offline when the webhook arrives | 503; Stripe retries; the catch-up fulfils it regardless |
| the database is away | the function fails; 503; as above |
| the same event twice | `duplicate`; nothing granted |
| a forged or wrongly signed request | 400; nothing queued |
| a fake event id in Redis | Stripe does not know it; refused |
| a price without `credit_usd` | the fulfilment fails and is retried; fixing the price lets the retry succeed |
| a refund after the credit was spent | the balance goes below zero |
| a dispute that is later won | not automatic: `studio:grant` |
| two subscriptions for one user | both invoices grant credit (both were paid); logged |
| Stripe is unreachable when a session is created | `billing_unavailable`; nothing changed |

## 9. Deployment

`deploy/server.env` gains `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`; `server:setup` gives the web both
and the worker the secret key only. The second migration is applied with `npm run db:migrate`.

## 10. Testing

- **Database** (local Supabase): the two kinds and the spend order; a reservation that spans a renewal; refunds
  including below zero and partial; every fulfilment function a no-op the second time; a renewal racing a
  reservation; a user cannot call any of the new functions or write the new tables.
- **Worker** (stand-in Stripe, Redis, Supabase): each event type; an unknown event id; a customer without a
  user; a price without metadata; the catch-up; two simultaneous customer requests.
- **Routes:** signature wrong, stale or missing; an oversized body; Checkout only for catalogue prices and the
  caller's own customer; a second subscription refused; the portal only for the caller.
- **Browser** (`test:accounts`, extended): a top-up bought through the stand-in's checkout page lands on
  `/account` with the credit and the payment; a second user sees none of it.
- **Setup:** the pure planner (what to create, replace or leave) from `plans.json` and a listing.
- **Existing suites** unchanged; without `STRIPE_SECRET_KEY` nothing of billing exists.
- **Live check (needs the owner's Stripe test keys and approval):** `stripe:setup`, a real Checkout in test
  mode, the portal, a webhook delivered to a reachable address, a refund.

## 11. Definition of Done

1. A signed-in user can subscribe or buy a top-up through Stripe Checkout and sees the credit without anyone
   running a command.
2. A renewal expires last month's unused plan credit and grants the new month's; top-up credit is untouched.
3. The same event delivered twice, a forged request, or a fake id in Redis grants nothing.
4. A refund takes its credit back.
5. `/account` shows the plan, the split balance and the payment history; the portal opens from it.
6. Without Stripe keys the studio is exactly 3.3; all tests in §10 pass; the README covers billing.

## 12. Risks and Unknowns (the prototype answers the first four)

- Whether the accounting of §4.2 holds under every interleaving of reserve, settle, renewal and refund (the
  database tests decide).
- Whether the webhook's raw body survives Next's request handling unchanged (the signature is over the bytes).
- How faithful a stand-in Stripe needs to be, and which fields of the real objects the fulfilment depends on.
- Whether a quick job's wait fits inside Stripe's webhook timeout with the worker's fetches in it.
- Unverifiable offline: the real API's shapes, Checkout and the portal, real delivery and retries, `stripe:setup`.

## 13. Prototype Findings (2026-10-08)

Built end to end in a scratch clone, one commit per task, against the local Supabase stack, a throwaway
`redis-server`, the real worker process and a stand-in Stripe: nothing reached Stripe, and no key of it exists
yet. Where this section and an earlier one disagree, this one describes what was built.

**What the unknowns of §12 turned out to be**

- **The accounting holds.** The database tests cover the spend order, a reservation that spans a renewal, a
  renewal racing a reservation, refunds (partial, repeated, below zero), and every fulfilment function called
  twice. One rule was added to §4.2: a month's credit first pays a balance that is below zero, and only what
  is left of it is credit that can expire (`plan_credit_usd = greatest(least(plan_credit_usd + g, balance), 0)`).
- **The raw body survives.** A route handler reads `req.body` as bytes before anything parses it; the
  signature verifies over exactly those. Nothing larger than 1 MB is read.
- **The stand-in Stripe** is one file (`web/test/stripe.ts`, ~350 lines): customers (with idempotency keys),
  prices, Checkout and portal sessions, charges, invoices, subscriptions, events, and — for setup — products,
  portal configurations and webhook endpoints. It also serves a checkout page that pays at once, calls the
  studio's webhook with a real signature and redirects back, which is what lets the browser test buy. The
  fields of real objects the fulfilment depends on are few and named in one place (`web/worker/billing.ts`):
  `event.{id,type,livemode,data.object.id}`, `customer.metadata.user_id`,
  `session.{mode,payment_status,customer,amount_total,line_items.data[0].{price,quantity},payment_intent.latest_charge}`,
  `invoice.{status,billing_reason,subscription,customer,amount_paid,charge,hosted_invoice_url,lines.data[0].price}`,
  `subscription.{status,customer,current_period_end,cancel_at_period_end,items.data[0].price}`,
  `charge.{amount_refunded,receipt_url}`, `dispute.{charge,amount}`, `price.{id,metadata}`. They are the names
  of API version `2024-06-20`, which every request pins. **Whether the real API answers in exactly these
  shapes is the first thing the live check must show.**
- **The wait fits.** A fulfilment is three to five requests to Stripe and one SQL call. The webhook route waits
  up to 25 s for the worker; if Stripe gives up sooner it retries, and the retry finds a duplicate.

**Where the built design differs from §1–§11**

- **The Stripe client lives in `src/billing/stripe.ts`,** not `web/server/billing/`: `stripe:setup` (a script
  under `scripts/`) uses it too, and `src/` cannot import from `web/`. The list of event types is there as
  well, so setup subscribes the webhook to exactly what the worker fulfils.
- **Setup has a second module, `src/deploy/stripe-apply.ts`** (reading the account and carrying the steps
  out), beside the pure planner. It is tested against the stand-in, including that a second run writes nothing
  but the portal's settings. `stripe:setup` takes `--yes`, `--dry-run` and `--live`; with a live key it
  refuses without `--live`.
- **The webhook endpoint is replaced when this machine does not hold its secret.** Stripe says a signing
  secret once, at creation; an endpoint whose secret is not in `.env` is of no use, so setup makes a new one
  (first) and removes the old.
- **The portal uses the configuration setup made**, found by `metadata.studio` and cached for five minutes,
  not the account's default: the API cannot make a configuration the default.
- **A plan change takes effect on the next invoice.** With the pinned API version the portal cannot schedule a
  change for the period's end; the configuration instead switches the price without proration. Nothing is
  charged or granted in between, the next month is billed and credited at the new plan — but the account page
  shows the new plan's name from the moment of the change.
- **A second subscription grants without ending the first one's month** (§8 said only "both grant"). The
  studio refuses to open a checkout for a second plan, but two checkouts opened side by side can both be paid.
  The second invoice then adds its credit, expires nothing, leaves the `subscriptions` row describing the
  first, and is recorded with the outcome `second_subscription` for the owner to act on.
- **`GET /api/account` gains `billing: true`** in a studio that takes payments (and nothing otherwise): the
  note under a paid button the user cannot afford then links to `/pricing` instead of the account page.
- **Deployment refuses half a setup:** `STRIPE_SECRET_KEY` without accounts, or without
  `STRIPE_WEBHOOK_SECRET` (the message says to run `stripe:setup`). `STRIPE_API_BASE` never reaches a server.
- **Outcomes** recorded in `stripe_events`: `fulfilled`, `duplicate`, `duplicate_payment`, `ignored`,
  `unknown_customer`, `other_subscription`, `second_subscription`, `unknown_payment`. An event for a payment
  that is not paid yet is not recorded at all (`not_paid`), so the later event or the catch-up fulfils it.

**Found on the way**

- Two database tests reused fixed subscription ids; the database is not emptied between runs, so the second
  run failed. Tests now make their own ids, as the 3.3 tests do.
- A 3.3 test (`a second stopped reroll is not free`) could stop its second job before the stand-in CLI had
  "submitted" it, because the first job's record satisfied what it waited for. It failed once under load; it
  now waits for this job's own submit.

**Known limits, accepted**

- A customer deleted in Stripe's dashboard leaves its user unable to buy (`billing_unavailable`) until
  `users.stripe_customer_id` is cleared by hand.
- A free checkout (a 100 % coupon) is never "paid" and grants nothing; promotion codes are not enabled.
- With two subscriptions, the first one's renewal expires what is left of the second one's credit as well.
- The web app holds the Stripe secret key (it opens Checkout and portal sessions). It still cannot grant credit.
- No tax handling; USD only; monthly plans only.

**Verification of the prototype.** `npm run typecheck` clean; `npx vitest run` 76 files / 678 tests with the
local Supabase stack, `redis-server` and Docker available (71 / 616 before this phase); `npm run test:e2e` 5;
`npm run test:accounts` 2 (one buys a top-up and a plan through the stand-in Stripe); `npm run test:stack` 2.
`npm run stripe:setup` was run against the stand-in: a dry run, a first run, a second run that changed
nothing, a declined prompt, and a live key refused. The plan
(`docs/superpowers/plans/2026-10-08-phase3.4-stripe-billing.md`) was generated from the prototype's six
commits and replayed task by task on a fresh clone, ending in a tree identical to the prototype's.

**Live check, still to do (needs the owner's Stripe test keys and approval):** `stripe:setup` on a real test
account; a real Checkout for a top-up and for a plan; the portal (cancel, change plan); a webhook delivered to
a reachable address and one redelivered; a refund; a test-clock renewal.
