# Phase 3.2 — Background Job Queue and Server Deployment — Design

Date: 2026-10-07 · Status: approved (sections 1–4), prototype pending · Builds on Phase 3.1 (`cb10e07`)

## 1. Goal

Run the studio on one server for one person: every pipeline action goes through a Redis-backed queue to a
dedicated worker, the web app holds no keys and starts no processes, and the whole thing comes up over HTTPS
behind one login with two commands. Local use (`npm run web`, the CLI) keeps working exactly as today, without
Redis.

The pipeline, its cache keys, the CLI's behaviour, the spend cap and the run lock do not change.

### Non-goals (later sub-projects)

Accounts, per-user data, quotas, billing; more than one worker or server; job priorities, scheduling, automatic
retries; monitoring and alerting; automatic pruning of old runs; zero-downtime deploys.

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | The worker runs the **CLI as a child process** per job (BullMQ only decides who runs when) | the live-verified path (`--cap`, lock, resume); a crashed job takes down only itself |
| D2 | **Disk stays the truth**: the worker writes the same `job.json` / `job.log` / `job.exit` as today; the queue adds only "waiting" and "active" | a run that finished is finished even if Redis lost track of it |
| D3 | **No retries, no automatic recovery**: `attempts: 1`, `maxStalledCount: 0` | a re-run of a paid job is how money is spent twice; a failed or interrupted run waits for Resume |
| D4 | Two queues: `runs` (long, default concurrency 2) and `quick` (seconds; the web request waits) | pricing and look changes stay responsive while renders are queued |
| D5 | One job per run through the **job id = run id**; finished jobs are removed from Redis at once | the queue itself refuses a duplicate, and the same run can be queued again later |
| D6 | One job interface, two implementations: `local` (3.1's detached spawn) and `queue`; `REDIS_URL` selects | local development and the existing tests need no Redis |
| D7 | **Exactly one worker**, enforced by a Redis guard; it clears every run lock at start | when the only worker starts, no CLI can be running, so every lock is stale by construction |
| D8 | One VPS, Docker Compose: `proxy` (Caddy), `web`, `worker`, `redis`; one data folder | cheapest layout that keeps runs as files |
| D9 | Login at the proxy (HTTP basic auth over HTTPS); the app's guard stays on with the public host name | protects every path at once without touching the pages; the guard remains if the proxy is misconfigured |
| D10 | Provider keys only in the worker's environment | the web container cannot spend or leak them |

## 3. Architecture

```
browser ─HTTPS─ proxy (Caddy: TLS + login) ── web (Next.js) ──┬─ reads ── data/runs, brand-kits, uploads
                                                               │
                                                               └─ BullMQ ── redis ── worker ── spawns `flowchain …`
                                                                                         └─ writes data/runs
```

### 3.1 Code layout

```
web/server/jobs/          types.ts (JobRunner, JobView), run-cli.ts (spawn + job files, shared),
                          local.ts (3.1's runner), queue.ts (BullMQ client side), index.ts (selects by REDIS_URL)
web/worker/               main.ts (entry), processors.ts (runs, quick), guard.ts (single worker, heartbeat),
                          sweep.ts (stale locks), redis.ts (connection)
web/lib/hosts.ts          the allowed-host rule (replaces lib/loopback.ts)
deploy/                   compose.yaml, compose.test.yaml, Caddyfile, web.Dockerfile, worker.Dockerfile,
                          server.env.example
scripts/server.ts         setup | deploy | backup
```

`web/server/jobs.ts` becomes `web/server/jobs/` with the same exported behaviour for the local case.

### 3.2 The job interface

```ts
type JobState =
  | { state: "queued"; position: number }      // new: waiting in line (queue runner only)
  | { state: "running" }
  | { state: "ended"; exitCode: number }
  | { state: "stopped" | "interrupted" };

interface JobRunner {
  readonly mode: "local" | "queue";
  start(runId, kind, args, approvedUsd?): Promise<JobView>;   // running (local) or queued (queue)
  stop(runId): Promise<JobView>;                              // ends a running job, or removes a waiting one
  view(runId): Promise<JobView | null>;
  cliText(args): Promise<string>;                             // free, short commands: plan, draft-modes, look
  health(): Promise<Health>;                                  // key names; in queue mode also redis and worker
  clearStaleLock(runId): Promise<void>;
}
```

`view` is async because, with web and worker in separate containers, a pid recorded by the worker means nothing
in the web container: in queue mode "running" comes from the queue (an active job with that id), "ended" from
`job.exit`, and a job record with neither is `stopped` or `interrupted`.

### 3.3 Run states

3.1's states plus `queued` (the last job is waiting in line). Everything else is derived as before.

## 4. The queues

| | `runs` | `quick` |
|---|---|---|
| jobs | `draft`, `generate`, `reroll`, `rerender` | `cli` (plan, draft-modes, look), `health` |
| job id | the run id (one per run) | generated |
| data | `{ runId, kind, args, approvedUsd?, enqueuedAt }` | `{ args }` |
| concurrency | `WORKER_CONCURRENCY` (default 2) | 4 |
| options | `attempts: 1`, `removeOnComplete: true`, `removeOnFail: true` | the same, plus the web's 60 s wait |
| result | `{ exitCode }` | `{ stdout }` |

Worker options for both: `maxStalledCount: 0` (a job whose worker vanished is failed, never restarted).

A CLI exit code of 1 (failed) or 2 (not confirmed) is a **result**, not a queue failure: the job completes with
`{ exitCode }`. BullMQ's own "failed" is left for infrastructure errors (the CLI could not be started; the worker
died).

Arguments never contain secrets (as in 3.1): keys are in the worker's environment.

## 5. The worker (`web/worker/`)

- **Start-up, in order:** connect; take the single-worker guard (`SET flowchain:worker <id> NX PX 15000`, renewed
  every 5 s; a second worker exits with a clear message); remove every `.lock` under `runs/` (D7) and log the
  runs it found locked; start the two consumers.
- **A `runs` job:** `run-cli.ts` writes `job.json`, removes any old `job.exit`, spawns
  `/bin/sh -c '"$@"; echo $? > "$JOB_EXIT_FILE"'` around the CLI in its own process group with output appended to
  `job.log` (exactly 3.1's code), and the processor awaits the exit. The exit code is returned as the result.
- **A `quick` job:** runs the CLI with `execFile` (60 s limit) and returns its stdout; a non-zero exit fails the
  job with the CLI's last error line, which the web turns into a `validation` error as today. `health` returns
  the missing variable **names** from the worker's environment.
- **Cancel:** the web publishes the run id on `flowchain:cancel`; the worker, if it holds that job, records
  `stoppedAt` and sends `SIGTERM` to the job's process group. A waiting job is removed by the web directly.
- **Heartbeat:** the guard key doubles as the heartbeat: no key means no worker.
- **Shutdown (`SIGTERM`):** stop taking jobs, wait for running ones up to `WORKER_DRAIN_MS` (default 30 min; the
  Compose `stop_grace_period` matches), then end the rest's process groups (they read `interrupted`), release
  the guard, exit.
- The worker has no HTTP port and never calls a provider itself.

## 6. The web side

- **`queue.ts`:** `start` re-checks nothing itself (the action layer already re-priced through `quick`) and adds
  the job with `jobId = runId`; an existing job with that id → `job_active`. `stop` removes a waiting job or
  publishes a cancel. `view` reads `job.json`/`job.exit` and asks the queue for the job's state and position.
  `cliText` adds a `quick` job and waits up to 60 s (`worker_offline` on timeout). Redis errors →
  `queue_unavailable` (503).
- **Health:** `GET /api/health` gains `queue: { mode, redis, worker }`. With the worker offline the pages show a
  banner and paid buttons are disabled with that reason.
- **Events:** the live feed keeps watching the run folder and, in queue mode, also re-reads the run every 2 s
  (queue position and the queued → running flip are not file changes).
- **The page:** a `queued` badge with "nth in line" and "Remove from queue"; everything else as in 3.1.
- **Hosts:** `STUDIO_HOST` (e.g. `studio.example.com`) is accepted next to the loopback names by both the request
  interceptor and `guard()`; unset, the rule is 3.1's. Writes still need `Sec-Fetch-Site: same-origin`.
- New error codes: `queue_unavailable`, `worker_offline`.

## 7. One pipeline change

The render stage deletes its working folder (`render/`: staged files and the Remotion bundle) after a successful
render. It is not among the stage's outputs or inputs, so no cache key changes; a failed render leaves it for
inspection.

## 8. Deployment

### 8.1 Compose (`deploy/compose.yaml`)

| Service | Image | Ports | Mounts | Environment |
|---|---|---|---|---|
| `proxy` | `caddy:2` | 80, 443 public | `Caddyfile`, `data/caddy` | `STUDIO_HOST`, `STUDIO_USER`, `STUDIO_PASSWORD_HASH` |
| `web` | `deploy/web.Dockerfile` | none published | `data/runs` (read-only), `data/brand-kits`, `data/uploads` | `REDIS_URL`, `STUDIO_HOST`, paths |
| `worker` | `deploy/worker.Dockerfile` | none | `data/runs`, `data/brand-kits` and `data/uploads` (read-only) | `REDIS_URL`, the provider keys (`env_file`), `WORKER_CONCURRENCY` |
| `redis` | `redis:7` | none | `data/redis` (append-only file on) | — |

`web` and `worker` restart `unless-stopped`; `worker` runs with an init process and
`stop_grace_period: 30m`. Health checks: web `GET /api/health`, redis `PING`, worker "the guard key is mine".

### 8.2 Images

- **web:** Node 25, the repo, `npm ci`, `next build --webpack`, `next start -H 0.0.0.0 -p 3131`. No ffmpeg, no
  Chrome, no keys.
- **worker:** Node 25, a current static ffmpeg/ffprobe (the pipeline's filters are tested against ffmpeg 8),
  the libraries headless Chrome needs, the browser Remotion renders with (fetched at build), the repo, `npm ci`;
  runs `node --import tsx web/worker/main.ts`.

### 8.3 Proxy (`deploy/Caddyfile`)

One site, `{$STUDIO_HOST}`: automatic HTTPS, `basic_auth` with the stored hash, `reverse_proxy web:3131` with
streaming responses unbuffered (the live feed). Alternative for a private network instead of a public port: bind
the proxy to the tailnet address (a documented setting, not built in 3.2).

### 8.4 Scripts (`scripts/server.ts`, reading `deploy/server.env`)

| Command | Does |
|---|---|
| `npm run server:setup` | installs Docker if missing; creates `/opt/flowchain` and the data folders; generates the login password (shown once) and stores its hash; writes the server's `.env` from `deploy/server.env`; installs the nightly backup timer; runs the first deploy |
| `npm run server:deploy` | copies the tracked files over SSH (`rsync` of `git ls-files`); `docker compose up -d --build`; waits for health; prints the URL |
| `npm run server:backup` | syncs `runs/`, `brand-kits/`, `uploads/` to the R2 bucket (also run by the timer) |

`deploy/server.env` (git-ignored; `deploy/server.env.example` is committed): `SERVER_HOST`, `SERVER_USER`,
`STUDIO_HOST`, `STUDIO_USER`, the provider keys, the R2 settings.

### 8.5 Manual, once

Rent the server (4 vCPU, 8 GB), point a DNS name at it, fill `deploy/server.env`.

## 9. Compatibility

No stage input changes; `test/unit/compat.test.ts` stays untouched. Without `REDIS_URL` the studio behaves as in
3.1 (the local runner is 3.1's code moved, with its tests). A run made on the server is an ordinary run folder.

## 10. Failure handling

| What dies or fails | Result |
|---|---|
| the CLI mid-job | exit code on disk; `failed`; Resume |
| the worker process mid-job | the container restarts and its children die with it; the job stalls and is failed by the queue; the worker's start-up sweep clears the lock; `interrupted`; Resume |
| a redeploy | the worker drains up to `WORKER_DRAIN_MS`; jobs cut off read `interrupted` |
| Redis while jobs run | running jobs finish and record their result on disk; new actions get `queue_unavailable` |
| the web app | nothing happens to jobs |
| the server | waiting jobs are still in line (append-only file); running ones read `interrupted` |
| the worker is offline when an action is clicked | banner; `worker_offline`; nothing queued for paid actions |
| a job waits while the plan changes | the cap applies when it runs: exit 2, `needs_approval` |

## 11. Testing

- **Existing suites** unchanged, on the local runner.
- **Unit (no Redis):** runner selection; `queued` in `stateOf`; the host rule with `STUDIO_HOST`; `run-cli`;
  the render folder clean-up; the pure parts of `scripts/server.ts` (config parsing, command lines).
- **Queue tests against a real Redis** (`npm run test:queue`; a throwaway `redis-server` if installed, else a
  container), with the stub CLI: one job per run; order and position; exit codes 0/1/2 as results; no retry;
  a killed worker → `interrupted`, not re-run; cancel waiting and running; `quick` round trip and timeout;
  a second worker refuses to start; the lock sweep; waiting jobs survive a Redis restart.
- **Whole stack** (`npm run test:stack`; Docker): `compose.yaml` + `compose.test.yaml` (HTTP on a local port,
  the stub CLI in the worker, a fixture data folder): 401 without the login; with it, a draft is generated
  through the queue and the page shows queued → working → done.
- **Images:** the pipeline's ffmpeg and render tests run inside the worker image once in the prototype.
- **Deployment files:** `docker compose config` and `caddy validate` run in the test script.
- **Live check (needs a server and approval):** setup, login, a free re-render, one generation, a redeploy
  during a job.

## 12. Definition of Done

1. `npm run server:setup` and `npm run server:deploy` bring up the studio on a server over HTTPS behind the login.
2. Every action goes through the queue there; the web container holds no keys and runs no CLI.
3. A third long job waits its turn and the page shows its position.
4. Killing the worker, Redis or the web app leaves every run resumable, with nothing bought twice.
5. `npm run web` and the CLI work locally as before, without Redis.
6. All tests in §11 pass; the README covers the server; the live check is recorded here.

## 13. Risks and Unknowns (the prototype answers the first four)

- BullMQ's behaviour for a job whose worker dies with `maxStalledCount: 0`, and how fast it is reported.
- Whether a job id equal to the run id dedupes while waiting **and** while active, and is reusable after removal.
- Whether the pipeline's ffmpeg and Remotion tests pass inside the worker image (Linux, another ffmpeg build,
  Chrome's libraries, fonts).
- Whether Next's webpack build and the `@src` imports work inside the web image, and file watching across
  containers on a shared folder.
- Unverifiable offline: the real server (Docker install, DNS, the certificate, `rsync` over SSH), the backup to R2.
