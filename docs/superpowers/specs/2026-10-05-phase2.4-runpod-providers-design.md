# Phase 2.4 — RunPod Serverless Providers: Design Spec

- **Date:** 2026-10-05
- **Status:** Approved (brainstorming sections 1–4); prototype verified offline (§14); live check pending
- **Scope:** Sub-project 2.4. Builds on Phase 1 (`2026-10-02-phase1-cli-poc-design.md`), 2.1, 2.2 and 2.3
  (`2026-10-05-phase2.3-retention-brand-design.md`, whose video profiles this extends).

## 1. Goal

Generate keyframes and clips on our own RunPod Serverless endpoints, with a commercially permissive model stack, at
roughly $0.20–0.35 per 4-scene video (today: ≈ $1.35 on fal/Kling), without changing the pipeline engine, the stage
order logic or the Remotion renderer, and without changing anything for existing runs.

### Non-goals

FLUX.1 [dev], PuLID, InstantID, IP-Adapter-FaceID, PhotoMaker V2, Pony, Juggernaut, CausVid, DMD2 (licences, §12);
a 720p video profile (later, as a new profile); per-job attribution of cold-start and idle billing; RunPod for the LLM
or TTS; autoscaling beyond `workersMax`; removing the fal providers.

## 2. Decisions

| Topic | Decision |
|---|---|
| Client | A thin RunPod queue client (`/run`, `/status`, `/cancel`) and two providers behind the existing `ImageProvider`/`VideoProvider` interfaces |
| Worker contract | Our own small JSON contract (`task: "keyframe" \| "clip" \| "fetch-models"`); ComfyUI graphs live inside the worker |
| Outputs | Workers upload to an S3-compatible bucket (Cloudflare R2) and return a 7-day presigned URL; the manifest stores only the URL |
| Provider choice | Frozen per run in `models.image` / `models.video` (`runpod:<endpointId>/<workflow>@<version>`); unprefixed ids are fal; `PROVIDER_MODE` and `--provider` only choose for new runs |
| Workers | One Python codebase in `workers/` on RunPod's `worker-comfyui` base image; image built by a GitHub Action into GHCR |
| Weights | On a RunPod network volume, seeded by the worker's `fetch-models` task; not baked into the image |
| Deployment | `npm run runpod:deploy`: idempotent, via RunPod's REST API, asks before creating billable resources |
| Keyframes | SDXL with one checkpoint per preset (RealVisXL V5, DreamShaper XL, Animagine XL 4.0), SDXL-Lightning 8-step, base pass at the SDXL bucket then a 1.43× detail pass to the keyframe size |
| Identity | A paid run-level `reference` stage renders one character portrait (or a brand kit supplies one); IP-Adapter plus-face SDXL (ViT-H) at weight ≈ 0.6 on every keyframe; continue scenes rely on the seam frame |
| Video | Wan 2.2 I2V-A14B, 480p, fp8, Wan2.2-Lightning 4-step LoRA, frames sized to the narration (4k+1, 33–81 at 16 fps), RIFE ×2 to 32 fps |
| Costs | Image profiles (new) and video profiles (2.3) frozen per run; RunPod jobs are charged `executionTime × GPU $/s` |
| Default | `PROVIDER_MODE` stays `fal` until the live check passes |

## 3. Architecture

### 3.1 RunPod client (`src/providers/runpod.ts`)

- `run(endpointId, input, policy, signal) → jobId`: `POST https://api.runpod.ai/v2/{endpointId}/run` with
  `{ input, policy: { executionTimeout, ttl } }`, header `authorization: Bearer <RUNPOD_API_KEY>`. Sent once; the
  signal aborts the HTTP request (same contract as the fal submit).
- `status(endpointId, jobId)`: `GET /v2/{endpointId}/status/{jobId}` → `{ status, output?, error?, executionTime?, delayTime? }`.
- `cancel(endpointId, jobId)`: `POST /v2/{endpointId}/cancel/{jobId}` (used by tooling only; see §7).
- Polling: every 3 s; statuses `IN_QUEUE`, `IN_PROGRESS` keep waiting; `COMPLETED` returns; `FAILED` and `TIMED_OUT`
  after execution started are billed → `UnusableResultError` (charged); `CANCELLED` → `NonRetryableError`; HTTP 404
  (result expired) → bucket recovery (§7); other HTTP errors follow `isRetryable`.

### 3.2 Providers

- `RunpodImageProvider` (`ImageProvider`): `prepare` reads the optional reference image and builds
  `{ task: "keyframe", workflow, prompt, width, height, preset?, seed?, reference? (base64 image) }`. The worker owns
  each checkpoint's negative prompt.
- `RunpodVideoProvider` (`VideoProvider`): `prepare` reads the chain image and builds
  `{ task: "clip", workflow, image (base64 PNG), prompt, frames, fps: 16, width, height, seed? }`; width × height is
  480 × 832 or 832 × 480, from the chain image's orientation.
- Both `wait` for `COMPLETED` and return `{ url, seed, costUsd }`, where `costUsd = executionTime / 1000 × $/s` of the
  endpoint's GPU (price table, §6).
- Input images are base64 inside the request; the largest (a 1088×1920 PNG chain image) is well under the 10 MB `/run`
  limit. The provider checks the encoded size and fails before submitting if it exceeds 9 MB.

### 3.3 Interface seams (the only changes outside the providers)

- `ImageRequest.referenceImagePath?: string` and `ImageRequest.preset?: PresetName`.
- `ImageOutput` and `VideoOutput` gain `costUsd?: number`. `runProviderJob` charges `result.costUsd` when present,
  otherwise the stage's estimate (fal, unchanged). Its log and error texts say "request" instead of "fal request".
- The keyframes stage passes the run's reference image and preset to the image provider; the reference's SHA-256
  enters the keyframe cache inputs only when a reference exists.
- Estimates read the run's image and video profiles (§6).
- Untouched: `src/pipeline.ts`, stage execution and caching logic, fit, captions, render, Remotion.

### 3.4 Provider routing (frozen per run)

- `models.image` / `models.video` for new RunPod runs: `runpod:<endpointId>/keyframe-sdxl@1`,
  `runpod:<endpointId>/clip-wan22-480p@1`. Unprefixed ids (every existing run) are fal.
- `providersFor(env, models)` picks the provider per id, so a run always talks to the provider it was created with,
  whatever `PROVIDER_MODE` says at resume, reroll or rerender time.
- New runs: `--provider fal|runpod` on `run`, else `PROVIDER_MODE` (default `fal`). RunPod mode needs
  `RUNPOD_API_KEY`, `RUNPOD_KEYFRAME_ENDPOINT`, `RUNPOD_CLIP_ENDPOINT` and the R2 settings (§4.4); fal mode keeps
  needing `FAL_KEY` only.
- The endpoint id and workflow version are part of the model id, so they are part of new runs' cache keys; redeploying
  a new version never touches older runs.

## 4. Workers and Deployment

### 4.1 Worker code (`workers/`, Python)

- Base image: RunPod's `worker-comfyui` base (ComfyUI included), plus pinned custom nodes: ComfyUI_IPAdapter_plus
  (IP-Adapter), ComfyUI-Frame-Interpolation (RIFE); Wan 2.2 uses ComfyUI's native nodes.
- `handler.py`:
  1. validates the input against the contract (unknown task or field → error, nothing generated);
  2. builds the versioned graph in code (`workflows.keyframe_graph`, `workflows.clip_graph`), so the wiring is
     unit-tested;
  3. runs it through the local ComfyUI API;
  4. for clips, encodes the saved frames to H.264 MP4 with ffmpeg (ComfyUI's own video nodes change between
     versions); uploads the PNG or MP4 to R2 at `flowchain/<job id>.<ext>`;
  5. returns `{ url (presigned GET, 7 days), seed, executionMs }`.
- `fetch-models` task: downloads a pinned list (`workers/models.json`: URL, target path, SHA-256) onto the network
  volume, skipping files already present with the right hash; returns what it fetched.
- Pure functions (validation, template filling, frame count, preset → checkpoint) are unit-tested with `pytest`.

### 4.2 Image build

A GitHub Action builds `workers/` on push to `main` (paths `workers/**`) and pushes
`ghcr.io/<owner>/flowchain-worker:<git-sha>`, `:latest` and `:w-<first 12 characters of the tree hash of workers/>`.
The deploy uses the last one: it names the worker's contents, so an endpoint never changes under a run (§15). The
image holds code and custom nodes only (no weights).

### 4.3 Deployment (`npm run runpod:deploy`)

Through RunPod's REST API, idempotently (finds existing resources by name and updates them):

1. network volume `flowchain-models` (≈ 80 GB) in one data centre;
2. one template `flowchain-worker` for both endpoints (image `ghcr.io/…:w-<tree hash>`; env with the R2 account and bucket,
   and the two R2 keys as RunPod secrets);
3. two endpoints: `flowchain-keyframe` (RTX 4090 class, 24 GB) and `flowchain-clip` (L40S class, 48 GB), each
   `workersMin: 0`, `workersMax: 2`, idle timeout 30 s (§15);
4. writes `RUNPOD_KEYFRAME_ENDPOINT` and `RUNPOD_CLIP_ENDPOINT` into `.env` (replacing existing lines, atomically);
5. runs `fetch-models` on each endpoint and waits for it (1 h execution cap).

Before creating anything it checks that the image is in GHCR and looks up all four resources; an ambiguous name or
a volume in another data centre stops it with nothing written.

It prints what it will create and the monthly storage cost first and asks for confirmation (`--yes` skips).

### 4.4 Manual one-time setup (accounts and keys only)

A RunPod API key (`RUNPOD_API_KEY`), a Cloudflare R2 bucket and S3 access key (`R2_ACCOUNT_ID`, `R2_BUCKET`,
`R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`), and the GHCR package made public (or a registry credential). The README
gives exact steps.

## 5. Models and Identity

### 5.1 Keyframes

| Preset | Checkpoint |
|---|---|
| `photorealistic_8k`, `cinematic_history`, `cyberpunk`, `dark_fantasy` | RealVisXL V5 |
| `3d_render` | SDXL base 1.0 (DreamShaper XL 1.0 has no single-file download on Hugging Face) |
| `anime` | Animagine XL 4.0 |
| none (runs scripted before 2.2) | RealVisXL V5 |

- SDXL-Lightning 8-step LoRA; base pass at 768×1344 (9:16) or 1344×768 (16:9); detail pass ×1.43 (denoise ≈ 0.35)
  and centre crop to the run's keyframe size (1088×1920 / 1920×1088).
- The preset prompt wording (2.2) is unchanged; each checkpoint has its own negative prompt in the worker.
- Seed: the run's shared seed (2.3).

### 5.2 Reference stage (character identity)

- New paid stage `reference`, after `script` and before `tts`. It is scene 1's job (a per-scene stage that applies
  to scene 1 only), so a run it does not apply to has no target at all and older runs never plan a paid step.
- Applies only when the run's image provider supports references (RunPod) and the run has characters
  (`styleBible.characters` is not "none") and no brand-kit reference.
- Renders one neutral, front-facing, waist-up portrait of the character bible in the run's preset and seed, plain
  background, 1024 × 1024, to `images/reference.png`; cache inputs: model, prompt, preset, seed, size.
- A brand kit may name a `reference` image (PNG/JPEG inside the kit); `run --brand` copies it to
  `runs/<id>/brand/reference.png` and freezes the path in the request; then the stage does not run.
- Every keyframe (scene 1, cut scenes, Mode 2 scenes) is conditioned on the reference with IP-Adapter plus-face SDXL
  (ViT-H) at weight ≈ 0.6. Continue scenes have no keyframe and carry the look through the seam frame.
- Limitation: plus-face keeps hair, face shape, clothing and colours, not exact facial identity.

### 5.3 Clips

- Wan 2.2 I2V-A14B (fp8), Wan2.2-Lightning 4-step LoRA, 480×832 (9:16) or 832×480 (16:9).
- Frames: `n = 4k+1`, the smallest ≥ `ceil(narrationSec / 1.25 × 16) + 1`, clamped to 33…81 (the fit step stretches
  ≤ 1.25×; narration longer than 81 frames × 1.25 / 16 ≈ 6.3 s uses the fit step's slow+freeze).
- RIFE ×2 interpolation to 32 fps in the worker; MP4 H.264.
- The fit step (unchanged) scales to 1080×1920; 480p is softer than Kling (a 720p profile is a later option).

## 6. Costs and Profiles

- Price table additions (`prices.json` can override; optional fields with no schema default, so price tables
  frozen into older runs hash as before, and `runpodRates` applies these defaults): `runpodKeyframeUsdPerSec` 0.000306 (RTX 4090),
  `runpodClipUsdPerSec` 0.000486 (L40S), `runpodKeyframeSec` 8, `runpodReferenceSec` 8, `runpodClipSecPerFrame`
  (initial estimate 1.5, measured by the live check), `runpodColdStartSec` 90 (counted once per endpoint per run in
  estimates).
- Image profiles (new, frozen per run, like 2.3's video profiles): `fal-flux@1` (today's per-megapixel price) for runs
  without one; `runpod-sdxl@1` (`runpodKeyframeSec × $/s`). The keyframes estimate and the `modes` planner use it.
- Video profile `wan22-480p@1`: `clipSec(narration)` = frames / 16; `costUsd` = frames × `runpodClipSecPerFrame` × $/s.
- Actual charges: `executionTime × $/s` per job (§3.2). Cold boot and idle time are not reported per job; the ledger
  stays labelled "estimated", and the live check compares it with RunPod's bill.

## 7. Guardrails

- Submit once, abortable, request id saved before waiting (unchanged `runProviderJob`).
- RunPod policy per request: `executionTimeout` 120 s (keyframe, reference) / 600 s (clip); `ttl` 1 h. This caps the
  cost of one job (≈ $0.04 / ≈ $0.29).
- Client wait: 10 min (keyframe, reference), 20 min (clip), to cover cold starts. On timeout the job is kept (not
  cancelled): `resume` polls it again; RunPod's caps bound the spend.
- Expired status (404 after RunPod's 30-minute retention): the provider presigns `flowchain/<jobId>.<ext>` in R2 and,
  if the object exists, uses it and charges the estimate; otherwise the error says to reroll.
- `workersMax: 2` per endpoint caps parallel spend. Stages run scenes sequentially (unchanged).
- The budget checkpoints are unchanged; they read the run's profiles.

## 8. CLI and Configuration

| Item | Change |
|---|---|
| `.env` | `PROVIDER_MODE=fal\|runpod` (default fal), `RUNPOD_API_KEY`, `RUNPOD_KEYFRAME_ENDPOINT`, `RUNPOD_CLIP_ENDPOINT`, `R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` (RunPod mode only) |
| `run` | `--provider fal\|runpod` |
| `doctor` | in RunPod mode or for RunPod runs: API key valid, each endpoint `/health` reachable, R2 put/get/delete of a tiny object |
| `status` | provider per run (`image runpod keyframe-sdxl@1`, …) and the image/video profiles |
| npm | `runpod:deploy`; `smoke:runpod` = 4 scenes, `--mode auto --provider runpod --style cinematic_history`, a character-driven topic, the example music bed |

## 9. Compatibility

Existing runs have unprefixed (fal) model ids, no image profile (→ `fal-flux@1`), no reference: their cache keys,
estimates and providers are unchanged. `test/unit/compat.test.ts` keeps its pinned hashes, unedited; new fal runs are covered by
`test/unit/new-run.test.ts`. Pre-2.4 runs keep resuming and rerendering for free.

## 10. Testing

- **TypeScript (offline):** a fake RunPod HTTP server (submit once, abort, every status, FAILED billed, TIMED_OUT,
  404 → fake bucket recovery, execution-time charge); provider request shapes (keyframe with base64 reference, clip
  frames/size); the 9 MB input guard; routing (fal runs stay on fal under `PROVIDER_MODE=runpod`); the `reference`
  stage with fakes (applies / skips); image profile and the `wan22-480p@1` frame formula; compat.
- **Python (offline):** `pytest` for validation, template filling, frame count, preset → checkpoint, `models.json`
  schema.
- **Not verifiable offline:** the ComfyUI graphs, the Docker build, RunPod deployment and real timings. These are
  proven only by the live check.
- **Live (paid, with the user's approval):** `npm run runpod:deploy`, then `npm run smoke:runpod`; record per-job GPU
  seconds, cold starts, cost per video, ledger vs RunPod bill, identity across cuts, 480p quality; update the price
  table's seconds with measurements.

## 11. Definition of Done

1. `npm test`, `npm run typecheck` and `pytest` pass; pre-2.4 runs resume and rerender for free.
2. `npm run runpod:deploy` creates the volume, templates and endpoints, seeds the weights and is safe to re-run.
3. A live `smoke:runpod` run is recorded in this spec with measured timings and cost; the user decides whether
   `PROVIDER_MODE=runpod` becomes the default.

## 13. Risks and Unknowns

- Timings are estimates (Wan 4-step clip ≈ 60–180 s; SDXL keyframe ≈ 5–10 s); the live check measures them.
- Cold starts from a network volume may be minutes; with `workersMin: 0` the first job of each endpoint per run pays
  for it.
- Wan 2.2 A14B fp8 on 48 GB is expected to fit; if not, the clip endpoint moves to an 80 GB class GPU (A100) in the
  deploy config and the price table.
- The worker graphs depend on custom-node versions; they are pinned by commit in the Dockerfile.

## 14. Prototype Findings (2026-10-06)

Built in a scratch clone of `f9c79d5`, one commit per task, before the plan was written
(`docs/superpowers/plans/2026-10-05-phase2.4-runpod-providers.md`, replayed task by task on a fresh clone).

- **Tests:** `npx tsc --noEmit` clean; `npx vitest run` 46 files / 303 tests (257 before); `npm run test:worker`
  26 Python tests. Rerender plans for both live runs (2.1, 2.2) made with the new code contain only free stages; the
  2.1-computed and 2.2-auto compatibility hashes are unchanged.
- **Verified against sources (not run on RunPod):** the `/run` body `{ input, policy: { executionTimeout, ttl } }`
  in milliseconds; REST v1 shapes for volumes, templates and endpoints; GPU ids `NVIDIA GeForce RTX 4090`,
  `NVIDIA L40S`; the base image `runpod/worker-comfyui:5.10.0-base` (5.11.0 is not on Docker Hub), ComfyUI at
  `/comfyui`, `/start.sh` running `/handler.py`; every graph node name and input (ComfyUI source, the Comfy-Org Wan 2.2
  template, ComfyUI_IPAdapter_plus at `a0f451a`, ComfyUI-Frame-Interpolation at `26545cc`); 12 weight files with
  SHA-256 and size from Hugging Face (≈ 62.6 GB, fits the 80 GB volume).
- **Deviations from the design as approved:**
  - Graphs are built in Python, not JSON templates (testable wiring).
  - The handler encodes MP4s with ffmpeg; frames come from `SaveImage`. RIFE uses the `RIFE VFI` custom node with
    `rife49.pth` baked into the image.
  - `3d_render` uses SDXL base 1.0.
  - The contract has no `negativePrompt` (the worker owns it) and `preset`/`seed` are optional.
  - `reference` is scene 1's stage rather than run-level (§5.2), so older runs keep rerendering for free.
  - One template serves both endpoints; only the two R2 keys are RunPod secrets (created through the v2 API).
  - The base image's `extra_model_paths.yaml` lacks `diffusion_models`, `text_encoders` and `ipadapter`; the worker
    ships its own.
  - The offline tests inject a fake `fetch` (an in-memory RunPod API) instead of starting an HTTP server.
- **Unverified until the live check:** the graphs on a GPU with the base image's ComfyUI version; the Docker build
  and GHCR push; the REST calls and the v2 secrets call with a real key; that `/status` reports `executionTime` in
  milliseconds; Wan 2.2 A14B fp8 fitting a 48 GB L40S; timings and cold starts (the price table's seconds are
  estimates); identity strength of IP-Adapter plus-face at weight 0.6; 480p softness after upscaling.

## 15. Final Review Changes (2026-10-06)

The whole-branch review found no compatibility or double-charge defect (it planned every run in `runs/` with the old
and the new code and got identical plans) and eight things to fix before live use. All are fixed; the suite is
`npx vitest run` 46 files / 330 tests and `npm run test:worker` 41 tests.

- **Reference reroll.** `reroll --stage reference --scene 1` buys a new portrait (and then new keyframes). Without it
  a failed or poor portrait left the run stuck. With a `--seed`, the portrait's seed follows the reroll count.
- **Rates frozen per run.** A new RunPod run stores the materialised RunPod rates in `modePrices`, so a later change
  of the defaults cannot change what an existing auto run buys. Fal runs store exactly what they did before.
- **Jobs that never ran cost nothing.** A `FAILED`/`TIMED_OUT` job without an `executionTime` is recorded at $0
  (it never reached a GPU); a failed job that did run is charged its measured time, as before.
- **Worker.** R2 settings are checked before any GPU work; uploads use `when_required` checksums (R2 rejects boto3's
  newer default); inputs, frames and the MP4 are removed on every path; ComfyUI is interrupted when a job is
  abandoned; weight downloads have a 60 s socket timeout.
- **Deploy.** Content-addressed image tag with a GHCR existence check (also catches a package that is still
  private); `.env` is written before the downloads; all lookups run before any write; a volume is only ever grown.
- **Design changes from §4:** idle timeout 5 s → 30 s, so the Wan weights are not reloaded between a run's clips
  (≈ $0.015–0.03 per run of idle billing); `fetch-models` cap 3 h → 1 h (finished files are kept, so a cut-off
  download resumes).
- **Known and deferred:** a job that is still queued when its scene is rerolled is not cancelled and can still run
  and be billed (≈ $0.04 / $0.29) without a ledger entry; the brand-portrait size check also applies to fal runs
  and leaves no headroom for the rest of the request; the `.env` temp file is briefly created with default
  permissions; estimates and charges read today's `prices.json` (only mode planning uses the frozen rates), as fal
  runs already do.
- **Added to the live check:** whether `GET /templates` needs `includeEndpointBoundTemplates`, whether endpoint names
  come back with a ` -fb` suffix, that a `TIMED_OUT` job reports `executionTime`, and per-job `delayTime` to judge
  the idle timeout.
