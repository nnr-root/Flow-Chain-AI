# Phase 3.3 — Multi-Tenant Architecture, Database and Authentication — Design

Date: 2026-10-07 · Status: approved (sections 1–4), prototyped (§14) · Builds on Phase 3.2 (`d2466d0`)

## 1. Goal

Turn the single-user studio into one that strangers can sign up for: accounts (Google and email/password)
through Supabase Auth, a Postgres database that records who owns which run and brand kit and how much credit
each user has, isolation that holds even against a user calling the database directly, and Cloudflare R2 as
the lasting home of uploads and finished media.

The pipeline, its cache keys, the manifest, the CLI, the spend cap, the run lock and the 3.2 queue's rules
(one worker, never retried) do not change. `test/unit/compat.test.ts` is not edited.

### Non-goals (later sub-projects)

Payments (Stripe) and self-service top-ups; teams, sharing a run with another user; account deletion and data
export; fair scheduling between users beyond a per-user job limit; more than one worker or server; importing
runs made in local mode into an account; an admin web page (credit is granted by a command).

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | **The server enforces tenancy; the database is an index.** The run's `manifest.json` stays the pipeline's truth; a `runs` row records the owner, a cached state and what has been charged | the cache, lock and resume logic that prevents buying twice is untouched |
| D2 | Two modes selected by `SUPABASE_URL`: **local** (3.1's single-user studio, no accounts, no database) and **multi-tenant** (requires `REDIS_URL`) | local development and every existing test need no Supabase |
| D3 | **Users can only read their own rows; every write goes through a SQL function** that checks the caller | a signed-in user can call Supabase's API directly with their own token; the database must be safe on its own |
| D4 | The web uses a **user-scoped** Supabase client for everything; the **service-role** key exists only in the worker's environment | row-level security applies to our own code; the web holds nothing that can read another user's rows |
| D5 | Credit is a **USD balance per user**; a paid job **reserves** its approved cap and is **settled** at its real cost; both are atomic SQL functions | two tabs or a double click cannot overspend; Stripe later only tops up the same balance |
| D6 | The amount charged for a run is **the manifest's total spend minus what was already charged for that run** (`runs.charged_usd`) | no number supplied by a client can lower a charge; settling twice charges nothing twice |
| D7 | Users cannot cancel a reservation; the **worker reconciles** open reservations that have no job | a user who could free a reservation while its job runs could spend the same credit twice |
| D8 | The worker runs a paid job only with a **matching open reservation** (run, user, cap) | a job put into Redis by other means cannot spend (closes the gap 3.2's review left) |
| D9 | **Disk to work, R2 to keep.** The worker builds in `runs/<userId>/<runId>`, then copies to R2 under `users/<userId>/`; the local folder is a cache that can be deleted and restored | the tested, resumable path stays; a run no longer depends on one server's disk |
| D10 | Files are served from disk when present, otherwise by a redirect to a **signed R2 URL** (5 minutes), always after the ownership check | previews stay fast; a link is never public |
| D11 | Uploads pass **through our server** to R2, not straight from the browser | the server decides a file's type from its content and enforces the limits, as in 3.1 |
| D12 | Something that is not yours **does not exist**: 404, never 403 | no way to learn which ids exist |
| D13 | **Open sign-up**, email confirmation required, a new balance of **0** | nobody can spend before credit is granted |
| D14 | At most **two long jobs per user** waiting or running (`STUDIO_USER_JOBS`) | one user cannot fill the line |
| D15 | Plain SQL migrations in `supabase/migrations/` and the Supabase JS client; no ORM | the money logic is SQL anyway; an ORM's connection would bypass row-level security |
| D16 | Hosted Supabase in production; the Supabase CLI's local stack (Docker) and MinIO in tests | everything except Google login and real email is verifiable offline |

## 3. Architecture

```
browser ──HTTPS──▶ Caddy ──▶ web (Next.js) ──▶ Supabase (Auth, Postgres; the user's own token)
                               │  ▲                    ▲
                               │  └── files on disk    │ service role
                               ▼                       │
                             Redis ◀──────────────── worker ──▶ CLI ──▶ providers
                                                       │
                                                       └──▶ R2 (users/<userId>/…)   web ──▶ R2 (uploads, signed links)
```

### 3.1 Code layout

```
supabase/
  config.toml                 the local stack's settings (auth: confirmations on in production, off in tests)
  migrations/0001_tenancy.sql tables, row-level security, functions, the sign-up trigger
web/
  lib/supabase/{server,browser,proxy}.ts   the user-scoped clients (cookies), session refresh
  server/tenant.ts            the current user, tenant paths, `requireRun(user, runId)`
  server/credit.ts            reserve; "can this balance cover it"
  server/store/{r2,sync}.ts   S3 calls (aws4fetch), store and restore of a folder, signed links
  server/jobs/…               job data gains `userId` and `reservationId`
  worker/tenant.ts            the service-role client: reservation check, settle, run rows, reconcile, clean-up
  app/(auth)/{login,signup,reset}/page.tsx, app/auth/callback/route.ts, app/account/page.tsx
scripts/studio-admin.ts       `studio:grant`
```

### 3.2 Modes

| | Local | Multi-tenant |
|---|---|---|
| Selected by | no `SUPABASE_URL` | `SUPABASE_URL`, `SUPABASE_ANON_KEY` (web), `SUPABASE_SERVICE_ROLE_KEY` (worker) |
| User | one implicit user | the session's user on every request |
| Run folder | `runs/<runId>` | `runs/<userId>/<runId>` |
| Jobs | local runner or queue | queue only (start-up fails without `REDIS_URL`) |
| Credit | none | reserve and settle |
| R2 | not used by the studio | uploads and results stored, restored on demand |
| Proxy login | Caddy basic auth (3.2) | none; Supabase sessions |

### 3.3 The request path (multi-tenant)

1. `web/proxy.ts` keeps 3.2's host rule and refreshes the Supabase session cookie. A page request without a
   session is redirected to `/login?next=<path>`; an API request gets 401 `unauthenticated`. Public paths:
   `/login`, `/signup`, `/reset`, `/auth/callback`, static assets.
2. `route({ write })` keeps the host and same-origin checks and resolves the user with `auth.getUser()` (a call
   to Supabase that verifies the token; the cookie's content alone is never trusted). Handlers receive
   `{ user }`.
3. A run, file, brand kit or track is looked up first through the user-scoped client. No row → 404. Only then
   is anything read from disk, at `runs/<user.id>/<runId>`; the user id in a path is never taken from the request.
4. A paid action re-prices (3.1), then calls `reserve_credit`; a refusal becomes `insufficient_credit`, and
   nothing is queued.
5. The job is queued with `userId` and `reservationId`.

## 4. Database (`supabase/migrations/0001_tenancy.sql`)

Amounts are `numeric(12,4)`.

| Table | Columns | Notes |
|---|---|---|
| `users` | `id uuid` (= `auth.users.id`), `email`, `balance_usd` default 0, `created_at` | a trigger on `auth.users` inserts the row |
| `runs` | `id text` primary key (the run id), `user_id`, `topic`, `state`, `charged_usd` default 0, `stored_at`, `created_at`, `updated_at` | `state` is a cache for the list page, written by the worker; the manifest is the truth |
| `reservations` | `id uuid`, `user_id`, `run_id`, `kind`, `cap_usd`, `status` (`open`/`settled`), `charged_usd`, `created_at`, `settled_at` | unique index on `run_id` where `status = 'open'` |
| `ledger` | `id bigint identity`, `user_id`, `run_id`, `reservation_id`, `kind` (`grant`/`reserve`/`settle`), `amount_usd` (signed), `balance_after_usd`, `note`, `created_at` | append-only |
| `brand_kits` | `id uuid`, `user_id`, `slug`, `name`, `created_at`; unique (`user_id`, `slug`) | files in R2 and the disk cache |
| `music_tracks` | `id text`, `user_id`, `name`, `bytes`, `created_at` | the tracks 3.1 kept in `uploads/music` |

### 4.1 Row-level security

Enabled on every table. One policy each: `select` where `user_id = auth.uid()` (`id = auth.uid()` for `users`).
No insert, update or delete policy exists, so direct writes are refused for everyone but the service role.

### 4.2 Functions

All are `security definer` with `set search_path = ''`.

| Function | Executable by | Does, in one transaction |
|---|---|---|
| `create_run(p_id, p_topic)` | authenticated | inserts the run for `auth.uid()`; a taken id raises `run_exists` |
| `reserve_credit(p_run_id, p_kind, p_cap_usd) returns uuid` | authenticated | locks the caller's `users` row; raises `not_found` unless the run is the caller's, `job_active` if the run has an open reservation, `too_many_jobs` if the caller has `STUDIO_USER_JOBS` open reservations, `insufficient_credit` if `balance_usd < p_cap_usd`; subtracts the cap; inserts the reservation and a `reserve` ledger row |
| `register_brand_kit(p_slug, p_name)`, `register_track(p_id, p_name, p_bytes)`, `remove_brand_kit`, `remove_track` | authenticated | insert or delete the caller's own row |
| `settle(p_reservation_id, p_run_total_usd)` | service role | if the reservation is open: charge = `greatest(p_run_total_usd − runs.charged_usd, 0)`; balance += cap − charge; `runs.charged_usd = greatest(charged_usd, p_run_total_usd)`; close the reservation; one `settle` ledger row. A closed reservation: no effect |
| `set_run_state(p_run_id, p_state, p_stored_at)` | service role | the worker's cache of a run's state |
| `grant_credit(p_email, p_amount_usd, p_note)` | service role | adds to the balance; `grant` ledger row |

A draft (the script, about $0.006) reserves a fixed `DRAFT_CAP_USD = 0.02`. Free jobs (re-render) reserve
nothing but still count against the per-user job limit through the queue.

A provider may charge slightly past a cap: `settle` charges the real amount, so a balance can fall below zero.
Reserving needs `balance_usd >= cap`, so such an account can do nothing paid until it is topped up.

## 5. Jobs per tenant

### 5.1 Job data and the worker

- `RunJobData` gains `userId` (a UUID, validated) and `reservationId` (present for paid kinds).
- Before starting a paid command the worker reads the reservation with the service role: it must be open, for
  this run and user, and its `cap_usd` must equal the command's `--cap` (a draft: `DRAFT_CAP_USD`). Otherwise
  the job is refused.
- The CLI is started with `RUNS_DIR=<runs>/<userId>`; quick commands likewise.
- After the CLI exits (any exit, stop included): read the manifest's total spend; `settle`; `set_run_state`;
  store the run folder in R2 (§6).
- The worker's lists (`active`, the held-runs key) are keyed by run id as in 3.2; run ids are unique across
  users because `runs.id` is the primary key.

### 5.2 Reconcile

At start-up and every minute the worker lists open reservations. One whose run has no job waiting and none
running (older than 60 s, so a job about to be queued is left alone) is settled from the manifest on disk:
this covers a job that was never queued, a worker that died, and a settle that failed because Supabase was
away. The same pass retries stores that failed because R2 was away (`runs.stored_at` older than the folder's
newest file).

### 5.3 Fairness

`reserve_credit` refuses a third open reservation per user. Free long jobs are limited by the web counting the
user's jobs in the queue before adding one. The line stays first-come, first-served.

## 6. Storage

### 6.1 Layout

| | Disk (working copy) | R2 bucket `STUDIO_BUCKET` (lasting copy) |
|---|---|---|
| Runs | `runs/<userId>/<runId>/` | `users/<userId>/runs/<runId>/` |
| Brand kits | `brand-kits/<userId>/<slug>/` | `users/<userId>/brand-kits/<slug>/` |
| Music | `uploads/<userId>/music/<id>.mp3` | `users/<userId>/music/<id>.mp3` |

The bucket is private and separate from RunPod's transit bucket (`R2_BUCKET`). It uses the same R2 account
keys unless `STUDIO_R2_*` are set.

### 6.2 Store and restore

- **Store** (worker, after every job): upload files that are new or whose size or modification time differs
  from the last store (recorded in `<run>/.stored.json`); skip `render/`, `.lock`, `.stored.json`. Then
  `set_run_state(..., stored_at = now())`.
- **Restore** (worker; a quick job `restore`): list the prefix and download what is missing. Used before a job
  when the run folder, a kit or a track is not on disk, and when a user opens a run whose folder is gone
  (the page shows "Restoring…").
- **Clean-up** (worker, daily): delete a run folder that is stored and untouched for `STUDIO_CACHE_DAYS`
  (default 14).

### 6.3 Serving

`GET /api/runs/<id>/files/...` after the ownership check: the file from disk with range support (3.1) when it
is there; otherwise 302 to a presigned `GET` for `users/<userId>/runs/<id>/<path>`, valid 5 minutes. The path
is checked against the run's published paths exactly as today.

### 6.4 Uploads

The web validates as in 3.1 (type by content, size limits), writes to the user's folder, uploads to R2, then
calls `register_brand_kit` / `register_track`. If R2 refuses, the local file is removed and the request fails
with `storage_unavailable`.

## 7. Pages

| Page | Does |
|---|---|
| `/signup` | email and password, or "Continue with Google"; then "check your inbox" |
| `/login` | both ways in; returns to `next` when it is a path on this site, else `/` |
| `/auth/callback` | exchanges the code of a Google login or an emailed link for a session |
| `/reset` | request a reset link; set a new password from it |
| `/account` | balance, the ledger (newest first), sign out |

The header shows the balance and the user's email. A paid button the balance cannot cover is disabled with
"This needs up to $X; you have $Y." In local mode none of these pages exist and the header is 3.1's.

## 8. Errors

| Code | Status | When |
|---|---|---|
| `unauthenticated` | 401 | no valid session |
| `not_found` | 404 | the run, file, kit or track is not the caller's or does not exist |
| `insufficient_credit` | 402 | the balance is below the approved cap |
| `too_many_jobs` | 429 | the user already has `STUDIO_USER_JOBS` long jobs |
| `storage_unavailable` | 503 | R2 could not be reached for an upload or a link |

## 9. Failure handling

| What is down or fails | Result |
|---|---|
| Supabase | nobody can sign in or load pages; running jobs finish; their cost is settled by the reconcile when it is back |
| R2 | jobs run and results stay on disk; the store is retried by the reconcile; uploads are refused; files not on disk cannot be served |
| the worker mid-job | 3.2's behaviour; the reservation is settled by the next worker's reconcile at what the run had spent |
| a job never queued after its reservation | the reconcile returns the cap |
| a user calls Supabase's API directly | reads return only their rows; writes are refused; `reserve_credit` can only hold their own credit until the reconcile returns it |
| Redis or the worker | as in 3.2 |

## 10. Deployment

- Caddy: HTTPS without `basic_auth` when `STUDIO_AUTH=supabase` (set by `server:setup` when `SUPABASE_URL` is
  given).
- `deploy/server.env` gains `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `STUDIO_BUCKET`.
  `server:setup` writes two key files: `web.env` (Supabase URL and anon key, the R2 keys, the bucket) and
  `worker.env` (the service-role key, the R2 keys, the bucket, the provider keys).
- `npm run db:migrate` applies `supabase/migrations/` to the project (`supabase db push`).
- `npm run studio:grant -- --email <address> --usd <amount> [--note <text>]`.
- By hand, once: create the Supabase project; enable the Google provider with a Google OAuth client and set the
  site URL and redirect URL; create the R2 bucket; put the keys in `.env`.

## 11. Testing

- **Existing suites** unchanged, in local mode.
- **Database** (`npm run test:db`; the Supabase CLI's local stack in Docker): the migrations apply from empty;
  a sign-up creates a `users` row with balance 0; user A cannot select, insert, update or delete any of user
  B's rows through the REST API with A's token; `reserve_credit` under concurrency cannot overspend, refuses a
  foreign run, a second reservation for a run and a third for a user; `settle` charges the difference, returns
  the rest, is a no-op the second time, and is refused for a user's token; `grant_credit` is refused for a
  user's token.
- **Routes with two users:** every run, file, event stream, action, brand kit and track route answers 404 for
  the other user's ids and 401 without a session.
- **Worker:** a paid job without a matching reservation is refused; cost is settled after success, failure,
  stop and a killed worker (reconcile); store and restore against MinIO; the daily clean-up; a restored run
  resumes.
- **Whole stack** (`npm run test:stack`, extended): two users in a browser; each sees only their own runs; a
  generation lowers only its owner's balance; a file served from R2 by a signed link after the folder is
  removed.
- **Live check (needs the accounts and approval):** sign-up with a real email, Google login, a paid generation,
  the ledger against the providers' invoices.

## 12. Definition of Done

1. A stranger can sign up, confirm their email, log in with Google or a password, and sees an empty studio
   with a $0 balance.
2. After `studio:grant` they can make a video; the ledger shows the reservation and the real charge.
3. No route, file link or direct Supabase call shows one user anything of another's.
4. A run restored from R2 onto an empty disk plays and can be resumed.
5. Local mode and all 3.2 behaviour are unchanged; all tests in §11 pass; the README covers accounts, credit
   and storage.

## 13. Risks and Unknowns (the prototype answers the first five)

- Whether `@supabase/ssr` sessions work in Next 16's `proxy.ts` in webpack mode, and what `auth.getUser()`
  costs per request.
- Whether the local Supabase stack can be started, reset and torn down reliably from a test's set-up, and how
  long it takes.
- Whether `security definer` functions with `auth.uid()` behave as designed under PostgREST, and whether the
  row lock in `reserve_credit` really serialises concurrent calls.
- `aws4fetch` against MinIO and R2 for streamed uploads of large files and for presigned `GET`s with range
  requests (the Player seeks).
- The manifest's total-spend figure: that it is monotonic across resume and reroll, so "total minus charged"
  is always the job's cost.
- Unverifiable offline: Google login, real email delivery, the hosted project's settings, the real bucket.

## 14. Prototype Findings (2026-10-07)

Built end to end in a scratch clone, one commit per task, against the Supabase CLI's local stack (Docker), a
throwaway `redis-server`, MinIO standing in for R2, and the stand-in CLI: nothing reached a hosted project or
a provider. Where this section and an earlier one disagree, this one describes what was built.

**What the unknowns of §13 turned out to be**

- `@supabase/ssr` works in Next 16's `proxy.ts` and in route handlers in webpack mode. **No Supabase client runs
  in the browser at all:** signing up, in and out, the reset and the Google redirect are the studio's own
  routes, which set the session cookies. The public key is therefore never built into a page (it could not be:
  the images are built without it).
- The local stack starts in about a minute once its images are there and applies the migrations itself. All test
  files share its one database and run side by side, so none wipes it: every test makes its own users and run
  ids and looks only at them. The local stack's sign-in rate limit (30 per 5 minutes) had to be raised in
  `supabase/config.toml`, which configures the local stack only.
- `security definer` functions with `auth.uid()` behave as designed through the REST API. Twelve simultaneous
  reservations of $0.30 against a balance of $1 succeed exactly three times: the row lock serialises them.
- `aws4fetch` uploads a file as a file-backed blob with `x-amz-content-sha256: UNSIGNED-PAYLOAD` (no double
  read), and its presigned `GET`s honour range requests; both verified against MinIO.
- The manifest's ledger only grows, so "total minus already charged" is the job's cost; a run restored from the
  bucket onto an empty disk and resumed is charged only its new spend.

**Changes to the design**

- **Tenancy on disk is by construction** (§3.3 step 3, §5.1): the current user lives in a per-request scope
  (`AsyncLocalStorage`, set by `route()`, by the pages' `forUser()`, and per job in the worker), and
  `roots()` returns that user's own folders (`runs/<userId>`, `brand-kits/<userId>`, `uploads/music/<userId>`).
  Code that touches them outside a user's scope throws. Every existing route is thereby isolated without being
  rewritten; a run of another user simply is not in the folder the route looks in. The database lookup of
  §3.3 step 3 is made where a row is needed (credit, a run that is not on disk), not on every file request.
- The session is verified with `auth.getClaims()`.
- `reserve_credit`'s per-user limit is `max_user_jobs` in a one-row `settings` table, not an argument (an
  argument could be raised by a user calling the function directly). `STUDIO_USER_JOBS` limits the queue's
  side, which also counts free jobs.
- The bucket is optional (`STUDIO_BUCKET`); without it a studio with accounts keeps everything on disk.
- A run that is not on disk is **restored when its owner opens it**, synchronously, by a quick job; there is no
  "Restoring…" state. In the list it shows as "Archived". A single file the disk lacks is still served by a
  redirect to a signed link (§6.3).
- The worker notes at start which run folders changed since they were last stored and stores them; at run time
  it retries failed stores in the reconcile pass.
- The CLI is started without `SUPABASE_*` in its environment.
- The web container's health check asks `/api/ping`, a public route that says nothing and asks nothing of the
  worker (`/api/health` needs a session with accounts).
- Deployment: a second proxy file, `deploy/Caddyfile.accounts`, without the proxy's login; Compose requires
  `CADDYFILE` to be named, so a studio can never come up without a login by accident. `server:setup` picks it,
  skips the proxy's password, and writes `web.env` (the public key, the bucket) beside `worker.env`.
- `npm run db:migrate` needs `SUPABASE_DB_URL` (the project's connection string).
- A studio without accounts answers `GET /api/account` with `{ account: null }`, so the pages can ask without
  an error in the console.
- `create_run` precedes `reserve_credit`: a draft refused for lack of credit leaves a run row in state
  `creating` with no folder. It is not listed (the list shows what is on disk, plus rows that are stored).
- Testing: the two-user browser flow is its own test (`npm run test:accounts`: local Supabase, Redis, the real
  worker, the stand-in CLI) rather than an extension of the Docker stack test, which keeps testing the
  single-login deployment and now also validates the accounts variant of the Compose and proxy files.

**Still unverified (needs the accounts, and approval):** Google sign-in; the confirmation and reset emails and
their links through `/auth/callback`; a session refreshed by the proxy after its token expired; the hosted
project's settings (site URL, redirect allow-list, rate limits); `supabase db push`; the real R2 bucket; the
cost of verifying the session on every request against a hosted project.
